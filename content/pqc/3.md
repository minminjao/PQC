# 양자 시대의 전자서명 — ML-DSA · FN-DSA · SLH-DSA

## 전자서명의 기본 구조는 그대로다

밥이 메시지 해시에 개인키로 서명하고, 앨리스는 같은 해시를 계산해 공개키로 검증합니다.

1. 서명자는 문서의 해시값을 계산합니다.
2. 개인키로 전자서명을 만듭니다.
3. 문서와 서명을 검증자에게 전달합니다.
4. 검증자는 같은 문서의 해시값을 다시 계산합니다.
5. 공개키로 서명을 확인합니다.

**왜 해시를 먼저 거치나**: 긴 문서를 그대로 서명하면 계산할 데이터가 너무 많습니다. 문서를 짧은 해시값으로 요약한 뒤 서명합니다. 내용이 조금만 달라져도 해시값이 크게 달라지므로 문서 수정 여부도 확인됩니다.

**개인키와 공개키의 역할**: 개인키는 '도장을 찍는 열쇠', 공개키는 '도장이 진짜인지 확인하는 도구'입니다.

> 🎛 인터랙티브 — 서명하고 검증하기
> 텍스트 상자에 문장을 입력 → 해시값이 실시간으로 바뀜 → "서명" 버튼 → "검증" 버튼(초록 체크).
> 문장을 한 글자 바꾸면 해시가 완전히 달라지고 검증이 빨간 X로 바뀌는 것을 체험.

**양자 시대에 달라지는 부분**: 흐름은 그대로입니다. 다만 RSA·ECDSA 대신 양자 공격에 안전한 **ML-DSA, SLH-DSA**(2024년 NIST 최종 표준), **FN-DSA**(표준화 진행 중)를 씁니다.

> 💡 핵심
> 서명 절차는 안 바뀐다. 바뀌는 것은 도장의 재질(알고리즘)과 도장의 크기다.

## ML-DSA (CRYSTALS-Dilithium) — 범용 표준

격자 기반(Module-LWE/SIS), NIST FIPS 204. 범용 전자서명·TLS 인증서·코드 서명에 쓰이는 **기본 선택지**입니다. 서명과 검증이 빠르고 구현이 단순하지만, RSA·ECDSA보다 키와 서명 크기가 큽니다.

> ⚠️ 보완 필요: 원본 23쪽 "ML-DSA 기본 개념 1"은 이미지 슬라이드라 텍스트를 추출하지 못했습니다. 키 생성·서명 구조 그림 설명을 여기에 추가하세요.

### 서명 시간이 매번 다른 이유 — 거부 샘플링

ML-DSA는 먼저 임시값을 이용해 **후보 서명**을 만듭니다. 그다음 후보 서명의 숫자들이 정해진 안전 범위 안에 있는지 검사합니다. 범위를 벗어난 후보는 버리고 새로운 임시값으로 다시 계산합니다.

- 어떤 후보는 첫 검사에서 바로 통과하지만, 어떤 후보는 여러 번 다시 계산합니다.
- 따라서 같은 크기의 메시지를 서명해도 처리 시간이 항상 같지 않습니다. **오류가 아니라 정상 동작**입니다.
- 이 과정이 최종 서명값에서 개인키 정보가 새는 것을 막습니다.

> 🎛 인터랙티브 — 다시, 다시
> "서명" 버튼을 누를 때마다 후보가 생성되고 범위 안이면 초록, 밖이면 빨강으로 표시 후 재시도. 10회 반복하면 시도 횟수 히스토그램이 쌓인다.
> 캡션: "ML-DSA의 안전성은 '실패를 감수하고 다시 하는' 설계에서 나오고, 그 비용이 서명 시간의 변동이다."

## FN-DSA (Falcon) — 가장 작은 서명

NTRU 격자 기반(SIS/GPV), NIST FIPS 206으로 표준화 진행 중. **서명이 작고 검증이 매우 빠른** 것이 강점이며, 구현과 부채널 방어 난도가 높은 것이 약점입니다.

> ⚠️ 보완 필요: 원본 25쪽 "FN-DSA 기본 개념 1"은 이미지 슬라이드입니다. Falcon의 트랩도어 샘플링 구조 설명을 추가하세요.

### 크기 비교 (NIST 보안 레벨 1 기준)

| 알고리즘 | 서명 크기 |
|---|---|
| FN-DSA-512 | 666 B |
| ML-DSA-44 | 2,420 B |
| SLH-DSA-128f | 17,088 B |

Falcon-512 서명은 ML-DSA-65(3,309 B) 대비 약 1/5입니다. 인증서 체인, 블록체인 트랜잭션, 저전력 무선처럼 **바이트 단위로 값을 치르는 환경**에서 결정적인 차이를 만듭니다.

### 어디에 쓰나
- **블록체인·원장**: 거래 서명을 여러 노드가 저장하므로 작은 서명이 저장공간과 통신량을 줄임
- **금융 거래·인증서**: 많은 서명을 처리해야 하므로 빠른 전송과 검증에 유리
- **임베디드·IoT**: 자원이 제한된 기기에서 전송량과 배터리 사용을 줄임

## SLH-DSA (SPHINCS+) — 가장 보수적인 서명

해시 기반, NIST FIPS 205. **안전성의 근거가 해시함수 하나뿐**입니다.

### 구조: 일회용 도장을 나무로 묶는다
- **일회용 서명 키(OTS)** — 하나당 딱 한 번만 사용합니다. 두 번 쓰면 비밀이 드러납니다.
- 이 일회용 키들을 머클 트리로 묶어 **루트 하나를 공개키**로 삼습니다.
- 메시지 해시로 잎을 무작위 선택하고, 그 잎에서 루트까지의 경로를 서명에 함께 담습니다.
- 상태를 기록하지 않아도(stateless) 재사용 확률이 무시할 만큼 낮게 설계돼 있습니다.

> 🎛 인터랙티브 — 도장 나무
> 잎이 여러 개인 트리. "서명" 버튼을 누르면 잎 하나가 무작위로 선택되고 루트까지의 경로가 강조된다. 사용한 잎은 회색으로 바뀐다.

### 네 가지 부품
| 부품 | 역할 |
|---|---|
| **WOTS+** | 해시 체인으로 만든 일회용 서명. 반드시 한 번만 사용 |
| **XMSS** | 여러 WOTS+ 공개키를 머클 트리로 묶어 루트 하나로 줄임. 잎을 쓸 때마다 인증 경로가 따라붙음 |
| **하이퍼트리** | XMSS 트리를 여러 층으로 겹쳐 쌓아 사실상 무한에 가까운 서명 개수를 감당 |
| **FORS** | 실제 메시지에 서명하는 층. 소수 횟수 사용을 허용해 상태 관리 없이도 안전 유지 |

> ⚠️ 보완 필요: 원본 29쪽 "SLH-DSA 기본개념 2"는 이미지 슬라이드입니다.

### 장점과 단점
- **장점**: 새로운 격자 공격이 나와도 영향을 받지 않음. 상태 관리 실수로 키가 노출되는 XMSS류의 위험도 없음
- **단점**: 크고 느림. 서명 하나가 8~17 KB이고 해시를 수만 번 호출해 생성·검증이 오래 걸림. 실시간 대량 서명에는 맞지 않음
- **적용**: 계약서·공공기록처럼 장기 보존 문서, 루트 인증서, 펌웨어 서명. 처리 속도보다 장기적 안전성이 중요한 곳

## 셋을 한눈에

| | ML-DSA | FN-DSA | SLH-DSA |
|---|---|---|---|
| 표준 | FIPS 204 | FIPS 206 (진행 중) | FIPS 205 |
| 기반 | 격자 (Module-LWE/SIS) | NTRU 격자 | 해시 |
| 공개키 / 서명 (레벨 1~2) | 1,312 B / 2,420 B | 897 B / 666 B | 32 B / 7,856~17,088 B |
| 강점 | 빠르고 단순, 범용 | 서명이 가장 작음 | 가장 보수적 안전성 |
| 약점 | 크기가 큼 | 구현·부채널 어려움 | 크고 느림 |
| 적용 | TLS 인증서, 코드 서명 | IoT, 블록체인, 대역폭 제한 | 루트 인증서, 펌웨어, 장기 보존 문서 |

> 🎛 인터랙티브 — 크기 비교 막대 (이 사이트의 핵심 위젯)
> 가로축 로그 스케일. RSA-2048, ECC P-256, ML-KEM, ML-DSA, FN-DSA, SLH-DSA, Classic McEliece의 공개키·서명(암호문)을 두 색 막대로 표시. 파라미터 셋 드롭다운.
> 해석 캡션: "격자는 균형형, 해시는 공개키 최소·서명 최대, 코드는 공개키가 홀로 거대."

> 💡 핵심
> 범용은 ML-DSA, 바이트가 비싼 곳은 FN-DSA, 오래 살아남아야 하는 신뢰 앵커는 SLH-DSA.

## 확인해 보기

1. ML-DSA의 서명 시간이 매번 조금씩 다른 이유는?
   - 정답: 안전 범위를 벗어난 후보 서명을 버리고 다시 계산하는 거부 샘플링 때문. 정상 동작이다.
2. 루트 인증서에 SLH-DSA를 권하는 이유는?
   - 정답: 해시함수 하나에만 의존해 가장 보수적이며, 격자 공격이 발견돼도 영향이 없기 때문.
3. IoT 센서의 서명에 가장 적합한 것은?
   - 정답: FN-DSA(Falcon). 서명이 666 B로 가장 작다.
